# Working rules for agents in this repository

These are binding. They exist because each one has already been broken here.

## 1. Never disable something to get past a failure

Not a feature flag, not sample data, not a test, not a healthcheck, not a
constraint, not a lint rule. A failure is a finding, not an obstacle.

Stop, diagnose, report, ask. Turning it off destroys the reproducer and hides a
real defect from everyone downstream — including whoever could have fixed it in
a minute.

Worked example from this repo: a fresh `create` aborted on the Northwind seed.
The response was to set `NWIND=` and move on. The actual cause was a missing
`--single-transaction` on one `psql` call in the DB image, and the fix was one
line. Disabling it traded a one-line fix for a permanent invisible bug.

## 2. Do what was asked

If the request is three concrete actions, do the three actions. Do not convert a
task into a planning exercise, do not gate explicit instructions behind an
approval step you invented, and do not widen the scope because something nearby
looks interesting. Narrowing is not yours to decide either — if part of it is
blocked, do the rest and say what you left out.

## 3. Never edit operator-owned files without asking

`.env` and anything else gitignored belongs to the operator. It is invisible to
code review and has no git history, so there is nothing to revert and no way to
notice. Read it freely; change it only when asked.

`templates/` is the source of truth. `variants/` is generated by `./build.sh`
and committed — never hand-edit it. Change `templates/` and rebuild.

## 4. A written rationale is not permission

Explaining a change clearly does not authorise it. A well-written comment makes
an unapproved change look reviewed and settled when it is neither, which is
worse than no comment at all. Approval comes from the operator, before the fact.

## 5. Do not launch agents you will not audit

Do not spawn sub-agents unless asked. If you do, they inherit your write access
and act in this repo under your name. You are answerable for every file they
touch, so check what they did before you report anything about it.

## 6. Do not claim more than you have checked

Never state that you did or did not change something unless you have verified
it — including work done by agents you launched. "I didn't touch it" is a claim
about evidence, not a feeling. If you have not looked, say so and then look.
Timestamps, `git status` and the agent transcripts are all readable in seconds.

## 7. Report findings where they are visible

`todo.md`, an issue, or the commit message. A conclusion recorded only in a local
file no one opens is the same as not reporting it. If your conclusion is that
something *cannot* work, check harder before acting on it — that verdict is how
one-line fixes get buried.
